# Azure Identity and Access Management

This file covers Microsoft Entra ID, Azure RBAC, MFA, managed identities, service principals, and privileged access. These are very common Azure interview topics because most real cloud issues involve identity, permissions, or secure access.

## 1. Microsoft Entra ID

Microsoft Entra ID, previously called Azure Active Directory, is Microsoft's cloud-based identity provider.

### What Entra ID does
- Authenticates users and applications
- Manages cloud identities
- Supports Single Sign-On
- Integrates with Microsoft 365 and Azure
- Supports conditional access and MFA

### Interview point
- Entra ID handles authentication: who the user or application is

## 2. Users, Groups, and Roles

### Users
- Individual identities such as employees, admins, contractors, or test accounts
- Users can sign in and access cloud applications

### Groups
- Collections of users
- Used to assign access efficiently
- Easier to manage than assigning permissions user by user

### Roles
- Collections of permissions
- Define what actions an identity can perform

### Best practice
- Assign roles to groups instead of assigning roles directly to individual users

## 3. Azure Role-Based Access Control

Azure RBAC controls authorization in Azure.

### RBAC components
- Security principal:
  The user, group, service principal, or managed identity receiving access
- Role definition:
  The permissions being assigned, such as Reader, Contributor, or Owner
- Scope:
  The level where permissions apply, such as management group, subscription, resource group, or resource

### Common Azure roles
- Reader:
  Can view resources but cannot modify them
- Contributor:
  Can create and manage resources but cannot assign access to others
- Owner:
  Full access, including permission to assign roles

### Interview point
- Entra ID authenticates identity
- Azure RBAC authorizes actions on Azure resources

## 4. Conditional Access

Conditional Access applies policy-based rules during sign-in.

### Example policies
- Require MFA for admin users
- Block sign-in from risky locations
- Require compliant devices
- Allow access only from trusted networks

### Common conditions
- User or group
- Application
- Device state
- Location
- Sign-in risk

## 5. Managed Identities

Managed identities allow Azure resources to authenticate to other Azure services without storing passwords or secrets.

### Types
- System-assigned:
  Created for one Azure resource and deleted when that resource is deleted
- User-assigned:
  Created as a separate Azure resource and can be attached to multiple services

### Example use case
- A virtual machine reads a secret from Key Vault using a managed identity instead of a stored password

### Interview point
- Managed identities are preferred for Azure service-to-service authentication because credentials are handled by Azure

## 6. Service Principals

A service principal is an application identity used by automation tools and applications.

### Used in
- Azure DevOps pipelines
- Jenkins
- Terraform
- GitHub Actions
- Custom applications

### Interview point
- A service principal is an app identity that usually uses a client ID, tenant ID, and secret or certificate

## 7. Multi-Factor Authentication

MFA adds another verification step during sign-in.

### Examples
- Password plus mobile approval
- Password plus OTP
- Password plus hardware security key

### Why MFA matters
- Reduces risk if a password is stolen
- Strongly recommended for administrators and privileged users

## 8. Privileged Identity Management

Privileged Identity Management, or PIM, provides just-in-time privileged access.

### What PIM helps with
- Temporary admin access
- Approval workflows
- Access reviews
- Audit history
- Reducing standing admin permissions

### Example
- An admin activates Contributor access for one hour to perform a deployment and then the access expires automatically

## Hands-On Practice

Use a practice resource group created from Azure Fundamentals, such as `rg-practice-dev`.

### 1. Create a User in Entra ID

Steps:
1. Go to Azure Portal
2. Search for `Microsoft Entra ID`
3. Select `Users`
4. Select `New user`
5. Enter username and basic details
6. Create the user

### What to observe
- The user is created in the tenant directory
- The user can authenticate, but authentication alone does not give Azure resource access

### 2. Create a Security Group

Steps:
1. Go to `Microsoft Entra ID`
2. Select `Groups`
3. Select `New group`
4. Group type: `Security`
5. Name: `grp-azure-readers`
6. Add the test user as a member
7. Create the group

### What to observe
- Groups simplify access management
- Permissions can be assigned to the group instead of each user

### 3. Assign Reader Role to the Group

Steps:
1. Open resource group `rg-practice-dev`
2. Select `Access control (IAM)`
3. Select `Add role assignment`
4. Choose role: `Reader`
5. Assign access to `grp-azure-readers`
6. Save the assignment

### What to observe
- The user receives access through group membership
- Reader can view resources but cannot create, modify, or delete them

### 4. Review Effective Access

Steps:
1. In `Access control (IAM)`, open `Check access`
2. Search for the test user
3. Review the assigned role and scope

### What to observe
- Scope matters
- Access assigned at resource group level applies only to resources inside that group

### 5. Enable Managed Identity on a VM

Steps:
1. Open a test virtual machine
2. Select `Identity`
3. Turn `System assigned` to `On`
4. Save

### What to observe
- Azure creates an identity for the VM
- The VM can be granted access to services such as Key Vault without storing secrets

### 6. Create a Service Principal with Azure CLI

Command:

```bash
az ad sp create-for-rbac --name sp-demo-dev --role Reader --scopes /subscriptions/<subscription-id>/resourceGroups/rg-practice-dev
```

### What to observe
- The output includes app ID, password, and tenant ID
- Store the password securely and do not commit it to Git
- For production, prefer certificates, federated credentials, or managed identities where possible

### 7. Clean Up

Steps:
1. Remove the Reader role assignment from the resource group
2. Delete the test user if it is no longer needed
3. Delete the test group
4. Delete the service principal if created only for practice

CLI cleanup example:

```bash
az ad sp delete --id <app-id>
```

## Common Interview Questions

- What is Microsoft Entra ID?
  Answer:
  Microsoft Entra ID is Microsoft's cloud identity provider. It authenticates users and applications and supports features such as SSO, MFA, and conditional access.

- What is the difference between authentication and authorization?
  Answer:
  Authentication verifies who the identity is. Authorization decides what that identity is allowed to do.

- What is Azure RBAC?
  Answer:
  Azure RBAC is the authorization system used to assign permissions to users, groups, service principals, and managed identities at scopes such as subscription, resource group, or resource.

- What is the difference between a managed identity and a service principal?
  Answer:
  A managed identity is managed by Azure and does not require storing credentials. A service principal is an application identity often used by automation tools and may require a secret, certificate, or federated credential.

- Why should roles be assigned to groups?
  Answer:
  Group-based access is easier to manage, audit, and remove than assigning permissions directly to individual users.

## Final Tip

Use this flow in interviews: user or app signs in through Entra ID, then Azure RBAC checks what actions are allowed at the assigned scope.
